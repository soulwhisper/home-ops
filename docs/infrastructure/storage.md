## <img src="https://fonts.gstatic.com/s/e/notoemoji/latest/1f5c4/512.gif" alt="🗄" style="width: 20px; height: 20px; vertical-align: middle;"> Storage Architecture

Storage spans two complementary layers: **distributed Ceph** for replicated block, filesystem, and object storage across the Kubernetes cluster; and **Synology NAS** providing NFS exports and S3-compatible object storage via VersityGW for backup destinations and shared bulk data.

### Rook-Ceph Cluster

The [Rook](https://rook.io) operator manages a 3-node Ceph cluster across `exarch-01`, `exarch-02`, and `exarch-03`. Each node contributes one **SK Hynix P41 2TB NVMe** device, partitioned into **2 OSDs per device** for balanced placement-group distribution. Every durable pool uses a **replication factor of 3** with **`failureDomain: host`**, tolerating the loss of an entire node without data unavailability. `ceph-cachepool` (below) uses two replicas for rewarmable data.

The operator ships with the [ceph-csi-drivers](https://github.com/ceph/ceph-csi-operator) Helm chart, which registers two CSI drivers under `storage-system.*.csi.ceph.com` — `rbd` and `cephfs` (`nfs` and `nvmeof` are disabled).

Ceph-level tuning:

| Setting | Value | Rationale |
|---------|-------|-----------|
| `bdev_enable_discard` | `true` | TRIM passthrough to NVMe |
| `bdev_async_discard_threads` | `1` | Offload discard from OSD worker |
| `requireMsgr2` | `true` | Encrypted on-wire messenger v2 |
| `network.provider` | `host` | Direct host network for OSD replication |

The Ceph dashboard (`ssl: false`) is exposed internally via an HTTPRoute on the `kgateway-internal` HTTPS listener, with its admin password sourced from 1Password through an `ExternalSecret`.

#### CephBlockPool: `ceph-blockpool`

The default block pool backs RWO (`ReadWriteOnce`) PVCs across all namespaces. Its StorageClass `ceph-block` is the cluster's **default StorageClass**.

```yaml
StorageClass:  ceph-block (default)
Provisioner:   storage-system.rbd.csi.ceph.com
FS type:       ext4
Binding:       WaitForFirstConsumer
Expansion:     enabled
Mount options: discard
Image format:  2
Image features: layering, fast-diff, object-map, deep-flatten, exclusive-lock
```

CSI secrets (`rook-csi-rbd-provisioner`, `rook-csi-rbd-node`) are auto-generated by Rook and referenced by name in the StorageClass parameters.

#### CephBlockPool: `ceph-cachepool`

A replicated scratch pool (`size: 2`, `failureDomain: host`, `min_size: 1`, `requireSafeReplicaSize: false`) for **rewarmable** cache/scratch data — jellyfin transcode, stirling-pdf and scrypted caches (via the `components/cache` PVC component), and the kopiur mover cache. The second replica keeps a copy available when one host is drained; a single-replica PG could instead lose all copies and block RBD teardown during the node reboot. It is not for durable data. `enableCrushUpdates: true` is required for these changes to update the CRUSH rule of an existing pool; after changes, verify the actual CRUSH rule and per-PG host placement before maintenance.

Persistent per-policy caches reduce repeated index downloads during frequent mover runs. `continueUpgradeAfterChecksEvenIfNotHealthy: true` bypasses Rook health checks cluster-wide; durable-pool health must be verified independently before Ceph upgrades.

```yaml
StorageClass:  ceph-cache
Provisioner:   storage-system.rbd.csi.ceph.com
FS type:       ext4
Binding:       WaitForFirstConsumer
Expansion:     enabled
Mount options: discard
```

#### CephFileSystem: `ceph-filesystem`

The `ceph-filesystem` resource provides a replicated filesystem with one active
and one standby metadata server. Its chart values describe a StorageClass but
do not enable its creation; the current rendered manifests do **not** include a
`ceph-filesystem` StorageClass. Do not select that class merely because the
filesystem and CephFS CSI driver exist. Shared application files use the
Synology NFS classes below.

The metadata server placement uses a `DoNotSchedule` topology spread across `kubernetes.io/hostname`, ensuring the active and standby MDS land on separate nodes.

#### CephObjectStore: `ceph-objectstore`

The RADOS Gateway (RGW) exposes an S3-compatible HTTP endpoint consumed via per-app `ObjectBucketClaim`s (component `ceph-bucket`) by **langfuse** and **open-webui**. It is not exposed via Ingress — all consumption is intra-cluster. Backup traffic (kopiur, CNPG) targets the NAS-hosted VersityGW instead.

```
Internal endpoint: http://rook-ceph-rgw-ceph-objectstore.storage-system.svc.cluster.local
Port:              80
Instances:         1
Data policy:       3 replicas, host failure domain
```

A companion `StorageClass` named `ceph-bucket` is registered for OBC (`ObjectBucketClaim`) usage, with extended configuration fields (`bucketOwner`, `bucketPolicy`, `bucketLifecycle`) enabled on the operator.

#### Volume Snapshots

The snapshot-controller operator is deployed with `installCRDs: true` and provides the cluster-wide snapshot infrastructure. A single `VolumeSnapshotClass` is created by the Rook cluster chart (CephFS snapshotting is disabled — only RBD volumes are snapshotted):

| SnapshotClass | Default | Driver | Deletion Policy |
|---------------|:-------:|--------|:---------------:|
| `ceph-block-snapshot` | yes | `storage-system.rbd.csi.ceph.com` | Delete |

kopiur uses `copyMethod: Snapshot` to stage an RBD point-in-time copy before
uploading it to Kopia. A CSI snapshot alone is not an independent backup or an
application-consistency guarantee.


### CSI Driver NFS — Synology Integration

The [CSI NFS Driver](https://github.com/kubernetes-csi/csi-driver-nfs) mounts Synology NAS exports directly into pods, providing RWX access to bulk data that lives on spinning disk rather than cluster-local NVMe. Two StorageClasses correspond to the NAS's two volumes:

| StorageClass | NFS Export | Mount Options |
|-------------|-----------|---------------|
| `synology-volume1` | `nas.homelab.internal:/volume1` | `nfsvers=4.1`, `softerr`, `noatime`, `nconnect=4` |
| `synology-volume2` | `nas.homelab.internal:/volume2` | `nfsvers=4.1`, `softerr`, `noatime`, `nconnect=4` |

Both classes use `subDir: ${pvc.metadata.name}` to isolate PVCs under the share, with `onDelete: retain` to prevent the provisioner from removing subdirectories when a PVC is deleted. Common mount tuning includes 128 KiB `rsize`/`wsize`, `actimeo=60` (attribute cache timeout), and `timeo=30`/`retrans=3` for soft-recovery. The Synology NAS limits NFS access to `10.10.0.0/24` with `MapAllToAdmin` for simplified UID mapping.

The StorageClasses have `reclaimPolicy: Delete`; `onDelete: retain` applies to
the NAS subdirectory, not to the Kubernetes PVC/PV binding. Deleting a claim
does not promise automatic rebinding to its old directory. PVC names must be
unique within each NAS share because `subDir` does not include the namespace.

#### Application Data and Lifecycle Boundaries

Application definitions and Secret references in Git are separate from the
files they consume. The namespace indexes select shared storage alongside
applications; see the [catalog](../application/catalog.md) for definition links.

| Data | Definition owner | Lifecycle expectation |
|------|------------------|-----------------------|
| Photos, video, music, documents and downloads | `media-apps/media-nfs` KS; NAS `/volume1/{photo,video,music,document}` and `/volume2/downloads` | Keep the shared claims and NAS files independent of an individual media application's deployment selection |
| Media application configuration and indexes | Application KS or HelmRelease; usually Ceph PVCs | Git/ESO-managed settings and rebuildable indexes may be recreated. Other application state in the same PVC needs a backup if it must survive; explicitly accepting its loss does not require preserving every old Kopiur snapshot |
| Transcode, machine-learning and mover caches | Application or kopiur controller; `ceph-cache` | Rewarmable, not a durable-data retention boundary |
| PostgreSQL and application RGW buckets | Shared CNPG cluster or application OBC | Separate business state; do not infer that it is disposable because media files are on NFS |

Jellyfin's `/config` is on Ceph while `/media` uses the shared NAS `video`
claim. That config volume also contains application database state; Git,
ESO/1Password and a library rescan cannot recreate all of it. See
[Jellyfin's backup guidance](https://jellyfin.org/docs/general/administration/backup-and-restore/).
Keep a usable Kopiur backup when that state matters, or explicitly accept its
loss for the application being retired. Rebuilding settings or indexes is not
a promise to restore application-owned state.

Immich's `/data` uses `photo`, but its PostgreSQL metadata is separate.
MeTube writes to subdirectories of `downloads`. Losing a cache, optional
snapshot or explicitly disposable application state is not the same as losing
the NAS library files.

This is a data-value boundary, not an instruction to delete resources. Any
service retirement still needs an explicit application or batch decision;
stopping an application must not silently remove `media-nfs`, its namespace,
the Secret supply chain or shared databases. NAS-side backup and offsite copies
are outside the Kubernetes PVC backup mechanism.

### kopiur — PVC Backup

[kopiur](https://github.com/home-operations/kopiur) (Kopia-native Rust operator)
provides automated PVC backup and restore for **21 application definitions**.
The reusable components are
[`backup/`](https://github.com/soulwhisper/home-ops/tree/main/kubernetes/components/kopiur/backup)
(referenced by each consumer's `ks.yaml`) and
[`shared/`](https://github.com/soulwhisper/home-ops/tree/main/kubernetes/components/kopiur/shared)
(attached once per consumer namespace). They use one shared `ClusterRepository`
named `nas`; this count does not include every chart- or operator-created PVC.

#### Architecture

A single cluster-scoped repository plus per-app resources generated from the `backup/` component:

1. **`ClusterRepository`** (`nas`, in `storage-system`): the shared kopia repository as a first-class CR — S3 backend (dedicated `kopiur` bucket, repository at the bucket root), encryption password from 1Password, operator-managed maintenance (quick hourly, full daily 03:00, `Asia/Shanghai`), and `moverDefaults.cache`: a persistent warm Kopia cache PVC (`ceph-cache`, 10Gi) per policy, inherited by every mover. Apps are separated logically by Kopia identity (`<policy>@<namespace>:/pvc/<name>`), not by bucket path.

2. **`SnapshotPolicy`** (`${APP}`) + **`SnapshotSchedule`**: the recipe (`repository: {kind: ClusterRepository, name: nas}`, CSI `copyMethod: Snapshot` via `ceph-block-snapshot`, `zstd-fastest`, keep-daily 14) and its cron invocation (every 6 hours, configurable via `KOPIUR_SCHEDULE`).

3. **`Restore`** (`${APP}-bootstrap`) + **`PVC`** (`${APP}`): the Restore is a passive volume populator, referenced by the working PVC's `dataSourceRef`. It selects the latest policy snapshot when available. The configured `onMissingSnapshot: Continue` also permits initial creation without a snapshot; a completed bootstrap is therefore not proof that old application data was restored. The resulting working PVC becomes the backup source.

```
┌──────────────┐    periodic    ┌─────────────────┐   Kopia snapshot   ┌──────────────────┐
│  Source PVC  │◄──────────────│ SnapshotSchedule │──────────────────►│ Synology VersityGW│
│  (ceph-block)│               └─────────────────┘                   │  s3://kopiur     │
└──────┬───────┘                                                      └────────┬─────────┘
       │                                                                       │
       │ restore-once                                                          │
       ▼                                                                       │
┌──────────────────┐    dataSourceRef    ┌─────────────────────┐               │
│  Working PVC     │◄───────────────────│ Restore (populator)  │◄──────────────┘
│  (ceph-block)    │                    │                      │
└──────────────────┘                    └─────────────────────┘
```

#### Retention

```yaml
retention:
  keepDaily: 14
```

Snapshots run every 6 hours; daily snapshots are kept for 14 days.

Each policy schedules quick repository verification on Sunday at 04:00
(`Asia/Shanghai`, inherited from the repository), with up to six hours of
deterministic jitter to spread NAS reads. `KOPIUR_VERIFY_SCHEDULE` overrides the
cron per application. Verification reads 100% of backed-up file contents with
two parallel workers and two file readers; it never overwrites the working PVC.
`.status.lastVerified` records content-integrity verification, not an application
restore drill. Isolated restore and application checks require a separate,
approved operation.

#### S3 Destination

kopiur backups target the Synology-hosted **VersityGW** S3 gateway at
`http://nas.homelab.internal:9000`, in the dedicated `s3://kopiur` bucket.
The bucket setup recipe is `just infra versity init` (with the endpoint set for
the intended gateway). S3 credentials are sourced from 1Password through the
`shared/` component: one `ExternalSecret` per consumer namespace materializes
`kopiur-repository-secret` for its movers. The shared repository references the
same Secret name in `storage-system`:

```
ClusterRepository.spec.backend.s3:
  bucket:   kopiur             # repository at bucket root
  endpoint: nas.homelab.internal:9000   (TLS disabled, LAN)
encryption password: <1Password encryption-cipher.kopiur>
AWS_ACCESS_KEY_ID:    <1Password app-user.admin_user>       (per-namespace ExternalSecret)
AWS_SECRET_ACCESS_KEY:<1Password app-user.admin_pass>
```

#### Monitoring

Backup freshness is metrics-based: `kopiur_policy_last_backup_success_timestamp_seconds` feeds the kopiur-slo and basement-health dashboards (policies stale beyond 25h are flagged). Tuppr upgrade plans gate node upgrades on kopiur Snapshot health: upgrades are paused while any Snapshot is `Running` or `Pending`.

### CNPG PostgreSQL Backup

[CloudNativePG](https://cloudnative-pg.io) backs up the 3-instance PostgreSQL cluster using the **Barman Cloud** plugin, writing directly to the same VersityGW S3 endpoint as kopiur.

```yaml
ObjectStore:      barman-cloud
Destination:      s3://postgres/
Endpoint:         http://nas.homelab.internal:9000
Retention:        30 days
WAL compression:  snappy, maxParallel: 8
Data compression: snappy, --min-chunk-size=50MB, --jobs=4
```

The `postgres` Cluster resource declares the plugin at the top level:

```yaml
plugins:
  - name: barman-cloud.cloudnative-pg.io
    isWALArchiver: true
    parameters:
      barmanObjectName: barman-cloud
      serverName: postgres-v1
```

S3 credentials live in the `cloudnative-pg` Kubernetes Secret (populated via ExternalSecret from 1Password). A `ScheduledBackup` triggers periodic full backups through the barman-cloud plugin. The weekly `postgres-backup-verify` CronJob checks the latest backup's `backup.info`, including `xlog_segment_size`, and requires complete archived WAL objects from `begin_wal` through `end_wal` with no gaps. It ignores unrelated retained ranges and timelines. This checks object presence, not base-backup contents, an actual PostgreSQL restore, or PITR beyond `end_wal`; `barman-cloud-check-wal-archive` is a new-server pre-flight check and is not used here. Prometheus alerts cover failed verification, stale verification, and entirely missing completion metrics.

The current
[`postgres` Cluster definition](https://github.com/soulwhisper/home-ops/blob/main/kubernetes/apps/database-system/cnpg-operator/cluster/postgres.yaml)
uses `bootstrap.initdb`, not `bootstrap.recovery`. Reapplying that definition
after data loss is not a database restore. A restore must explicitly select the
backup/archive source, preserve the required extensions and credentials, and
verify database startup and application queries in an approved target.

Do not apply that requirement to a media application's deliberately discarded
cache or rebuildable configuration. Keep PostgreSQL business state and the NAS
library separate from optional application snapshots. The archived Woodpecker
DR workflow is historical reference, not evidence of a currently scheduled
restore drill.

### Synology NAS Services

The Synology DS1825+ runs several Docker Compose services critical to the storage stack:

#### VersityGW (S3 Gateway)

[VersityGW](https://www.versity.com) provides an S3-compatible API server backed by the local POSIX filesystem at `/volume3/docker/versitygw`. It serves as the **single S3 backend** for both kopiur and CNPG, running on port `9000` with a web UI on `9001`. Configuration is stored in a sops-encrypted env file (`versitygw.sops.env`).

Three S3 buckets are pre-created via the `infra.just` justfile:

```
BUCKETS: postgres  kopiur  zot
```

#### Zot Registry (OCI Mirror)

A single [Zot](https://zotregistry.dev) instance acts as a **pull-through cache** for `docker.io`, `ghcr.io`, `quay.io`, `registry.k8s.io`, and `factory.talos.dev`, storing images in the VersityGW S3 `zot` bucket with daily garbage collection and tag retention (5 most recently pushed / 3 most recently pulled per repo). It is the second LAN hop of the node pull chain — `containerd → spegel (P2P) → zot → upstream` — wired via the Talos private mirrors patch (`infrastructure/talos/prod/30-private-mirrors.yaml`): endpoints are `http://nas.homelab.internal:9002/v2/<upstream>` with `overridePath: true`, and `skipFallback: false` lets pulls fall back to the upstream registry when zot or the NAS is down. On-demand sync caches images on first request; `http.compat: ["docker2s2"]` preserves upstream manifest digests and signatures for digest-pinned pulls. Metrics are scraped via the `zot` ScrapeConfig (`up{job="zot"}` doubles as liveness); the zot UI shares port `9002`.

#### Scrutiny (SMART Monitoring)

[Scrutiny](https://github.com/AnalogJ/scrutiny) monitors the health of the Synology's NVMe (`/dev/nvme0`, `/dev/nvme1`) and SATA (`/dev/sata1`, `/dev/sata2`) devices via the `starosdev/scrutiny` omnibus image, with direct device passthrough and udev access.

### Talos Disk Layout

Each MS-01 node boots from a 256 GB industrial SSD. Production Talos configs pin no volume sizes or user volumes — `EPHEMERAL` and system partitions use Talos defaults, and all workload storage comes from Ceph or NFS. The **test** environment is the only one that sizes volumes explicitly (`infrastructure/talos/test/10-general.yaml`):

| Volume | Size | Purpose |
|--------|:----:|---------|
| `EPHEMERAL` | 512 GiB | Container runtime root on the virtual disk |
| `local-hostpath` | 256 GiB | Local hostpath user volume (virtual disk) |
