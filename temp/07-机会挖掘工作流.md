# 07 机会挖掘工作流（follow-up 计划，P6）

> 定位：把"AI 筛需求"做成一套**数据进 git、打分可审计、门禁在人**的常驻工作流。
> 哲学与 reviewer 同构：LLM 出结构化评分，人做金标校准与最终立项门禁。
> 依赖：P0（Forgejo 可用）+ 04（飞书按钮）；**不依赖** reviewer 门禁。
> 可在 P2 shadow 期间并行启动 P6.0 手动期。

## 核心判定（来自两轮案例分析，作为工作流的设计前提）

- 风口真实形态：**验证成本极低、分发成本极高**。AI 的正确位置在筛选层和成本层，
  不在决策层和分发层。
- 唯一可信需求信号：**"人们已在为相邻方案付费且不满"**；嘴上的抱怨按零处理。
- 唯一真护城河：**分发可达性**（AbMaxx 案例：$54K/月流水、LTV $30、7 倍月流水
  急售——ASO 窗口是真资产，AI 扫描只是钩子）。
- 收入核验工具（TrustMRR/whatsthe.app，RevenueCat 数据源）是双刃剑信号源：
  证明 niche 需求真实，也意味着窗口已被人占了一半。
- 判真规则：无第三方核验的自报收入截图一律按 LARP 处理，不进样本库。

## 数据模型（git 为底座，审计链天然）

新建 **GitHub PRIVATE 仓库 `opportunities`**（不复用 draftbox——笔记库与机会生命周期
不同；出域例外拍板项 D6，先例 chat-platform/silent-soil；执行面 = GHA + tailnet 回传，
与主架构同构）：

```
opportunities/
├── AGENTS.md                  # 工作流规则 + 打分卡定义（单一来源）
├── items/<id>.yaml            # 痛点条目: {人群, 现状替代方案, 抱怨频次,
│                              #   是否提及付费, 来源链接[], 采集时间, 信号源}
├── scores/<id>.yaml           # {痛点强度, 付费意愿, 市场容量核算, 竞争密度,
│                              #   分发可达性, verdict: pursue|watch|kill,
│                              #   confidence, model, 时间}
├── calibration/               # 金标集: LLM 判定 vs 人工复核对照 + 假阳性率记录
└── kills/                     # 毙掉留痕（含原因），防重复挖同一坑
```

批次节奏：每轮采集+初筛产出一个分支 → PR（diff=新增条目/分数）→ 人工扫摘要
merge。**merge 即入库，PR 即审计**——与主计划同一套 git 底座哲学。

## 五层管道 → 现有基建映射

| 层 | 实现 | 运行体 |
|---|---|---|
| L1 采集（确定性，无 LLM） | Firecrawl（已有，MCP+内部端点）+ SearXNG（已有）+ 源适配器脚本 | **GitHub Actions** `schedule`（周）+ `workflow_dispatch`（指定 niche 手动挖），经 `tag:gha-ci` 摸 agentgateway |
| L2 结构化初筛 | **omni 车道**批处理：抱怨→痛点四元组（extraction 是 omni 的 lane-fit 定位） | 同工作流 step |
| L3 打分卡 | **规则优先**（确定性 python：TAM 核算、竞品计数、容量一票否决）+ **complex 车道**综合 verdict `{pursue\|watch\|kill, confidence}` | 同工作流 step |
| L4 金标校准 | 首批 20 条人工复核入 `calibration/`；假阳性率超标→迭代 prompt/阈值 | 人工 + PR 评论留痕 |
| L5 零代码验证 | 纯人工：落地页+等待名单/私信预售/挂单测试；**14–30 天第一笔钱才进开发**；结果回写 `items/` | 人工 |

## 打分卡硬规则（写死进 AGENTS.md，机器执行不问模型）

1. **容量一票否决**：niche 人数 × 客单价 × 现实转化率 < $1K/月 → kill。
2. **付费意愿计分**：仅"已在为相邻方案付费且不满"计 1；"免费凑合中"= 0。
3. **分发可达性一票否决**：写不出"前 10 个用户从哪个渠道来"→ 直接降级。
4. **低置信升级**：confidence < 0.8 → 飞书审批卡片（复用 04：深入/毙掉/转人工）。
5. **优先信号加权**：marketplace 搜索长尾（App Store/Chrome/VS Code——存量分发，
   冷启动最稳）与收入核验命中（TrustMRR 类）加权；软文样本零权。

## 信号源清单

| 源 | 信号 | 采集方式 |
|---|---|---|
| G2/Capterra/应用商店差评 | "每年付 $500 就为这一个功能"=立项书 | Firecrawl |
| Reddit/V2EX/知乎/X 抱怨 | 跨平台跨时间**重复**才算 | Firecrawl/SearXNG |
| 工具接缝 | 两个流行工具无集成 | 手动提名 + dispatch |
| marketplace 搜索长尾 | 上架即获客的存量分发 | 各商店搜索建议/长尾 |
| TrustMRR/whatsthe.app | RevenueCat 核验收入=需求真实+窗口占位 | Firecrawl |
| 关键词缺口 | 有搜索量无像样供给 | SEO 工具（手动喂入） |

## 铁律（防跑偏）

1. 立项门禁在人：模型只出评分与证据，人做 pursue 决定。
2. **第一笔收入验证先于一切开发投入**——管道产物是"验证任务"，不是"产品"。
3. 禁止用管道批量生成产品匹配高分痛点：薄壳是被商品化绞杀的第一层；
   分数花在手动验证+手动分发上。
4. 先手动跑 20 条金标校准，假阳性率达标（<20%，痛点筛选容忍度宽于代码审查）
   再写采集自动化——与全计划"先手动后自动"一致。

## 阶段

| 阶段 | 内容 | 验收 |
|---|---|---|
| P6.0 手动期 | 工作站 omp + Firecrawl 手动挖一个 niche 全流程；攒 20 条金标 | 金标假阳性率 <20% |
| P6.1 建仓 | `opportunities` 仓库 + 数据模型 + L2/L3 脚本手动跑通 | 一个批次走完 分支→PR→merge |
| P6.2 事件化 | Actions schedule + dispatch；飞书周报卡片（top 条目+按钮）；低置信升级接通 | 连续两周周报无垃圾推送；卡片按钮写回 PR 闭环 |

## 与主计划的复用关系

- 车道纪律（06）：omni 初筛 / complex 打分 / micro 分类，全走 agentgateway。
- 飞书按钮（04）：低置信请示与周报卡片复用同一回调+审计写回链路。
- 验证协议（06 闸三）：金标→shadow→自动档，同构套用。
- Langfuse：每批次打分 span 入库（决策类 always_on），校准数据反哺阈值。
- CI 凭证：复用 environment `ci-llm` / CI 专用 key / `tag:gha-ci` ACL，不新建通道。
